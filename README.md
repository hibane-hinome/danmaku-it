# danmaku-it（原 sc_collector）

独立的 B 站直播间「醒目留言（SC）」旁路采集器。自己连弹幕服务器，不依赖浏览器、不修改 `sc_catch` 扩展。

## 特性

- 直接连弹幕服务器：只需要 `buvid` + WBI 签名。**界面里有账号时用账号的 cookie 连**（否则 B 站会把普通弹幕的昵称打成 `青***`，粉丝牌/舰长信息也拿不到）；命令行默认匿名
- 多房间并发采集，每房间独立重连
- 正确解包 `pv0` / `zlib` / `brotli` 三种协议
- 30 秒心跳，断线指数退避重连（1s → 60s，带抖动）
- 只落 `SUPER_CHAT_MESSAGE`，同时记录 `SUPER_CHAT_MESSAGE_DELETE` 便于事后校对
- SQLite 落库，`sc_id` 主键去重，重连不会重复写入
- 导出 NDJSON / CSV，便于翻译校对与 RAG 使用
- 全量原始 JSON 保留（`raw_json`）
- 界面把表情弹幕直接画成图片（地址来自报文的表情字段与 `extra.emots` 表），只在内存里流转，不落库
- **能在弹幕机上直接发弹幕**，不用开直播间网页：底部输入框 + Enter 发送，限 80 字符、约 1 秒一条
  （采集和发送走同一个账号 cookie；缺 `bili_jct` 时用 SESSDATA 自动换一个）

## 配置

`config.json` **不入库**（含 cookie 路径与本机窗口状态），首次使用从模板复制：

```bash
cp config.example.json config.json
```

模板里 `database` 用相对路径指向同一工作区的归档库，`rooms` 换成要采集的直播间：

```json
{
  "rooms": [22748536],
  "database": "../live-archive/.data/translation_history.db",
  "log_file": "logs/collector.log",
  "cookie_dir": "accounts",
  "log_level": "INFO",
  "heartbeat_seconds": 30
}
```

- `rooms` 可填短号或真实房间号，程序会用 `getInfoByRoom` 解析成真实 `room_id`；填 `0` 进入离线回放，从库里读真实 payload 走同一套解析，不联网也不写库。
- `database`、`log_file`、`cookie_dir` 的相对路径都基于 `config.json` 所在目录解析，也可写绝对路径。
- `cookie_dir` 是**账号目录**：把浏览器导出的 cookie 文件（一个账号一个 `.csv`）丢进去，启动时自动扫描，界面上的账号下拉可以随时切换。**发弹幕必需**；采集也用它（登录态才拿到完整昵称和粉丝牌），见下一条。支持两种布局：标准 Netscape（7 列）和 Chrome 扩展导出的 13 列格式，代码按首列是否为域名自动区分。
- 只有含 `SESSDATA` 的 csv 才算有效账号；其余文件不会被当成账号。
- **不打算发弹幕就不建这个目录**：目录为空或不存在时是纯匿名采集，界面的发送行会提示「账号目录里没有可用账号」，弹幕列表里的昵称则会被 B 站打码成 `青***` 这种。
- `send_color` / `send_mode` 记的是上次选的弹幕颜色（十进制 RGB）和位置（1 滚动 / 4 底部 / 5 顶部），`send_medal` 记上次选的粉丝牌 id（0 = 不切换），界面里改了就写回。实际能不能用由房间决定，见「在弹幕机上直接发弹幕」。
- **模板文件本身不会被写回**：`config.example.json` 只读，界面的窗口位置与宽高、栏高这些只会存进 `config.json`，所以可以直接拿模板试跑而不会污染它。

表结构由 `collector/storage.py` 在首次写入时自动创建，指向一个空文件也能直接用。

  正文里夹着的 `[大哭]` 这类小表情从 `info[0][15]["extra"]` 的 `emots` 表里拿图（老版本
  B站把这个表藏在 `info[0][13]["emots"]`），payload 里没有的（更老的小表情）再拿本房间
  表情包兜底；对不上图的 `[名字]` 先按青色文字显示，图下好后自动补画这一行，不会卡住后面的弹幕
- **自己发的弹幕整行高亮**：按账号 uid 认，行首加一条竖杠 `▌`，在一堆滚动弹幕里一眼能找到自己那条
- **弹幕列表不显示发送者头像**：头像是一人一图、种类数等于人数，缓存几乎不命中，量大了得不偿失；表情种类有限、重复率高，才值得缓存。账号下拉里的头像只有寥寥几个，不在此列
- 表情图缓存在 `cache/images/`（原始字节，按 URL 哈希命名），同一个 URL 只下一次，下次开播直接用；删掉这个目录没有任何副作用
- 三栏（弹幕 / 事件 / 醒目留言）可按住标题左侧的 ⠿ 手柄上下拖动换顺序；栏高、顺序与显隐都会记住，顶部「菜单」可隐藏整栏
- 醒目留言与弹幕同样是日志流，每条以粗分隔线隔开，≥100 元加粗橙色高亮
- 顶部「置顶」切换悬浮层级，按钮按状态变文案（置顶 / 已置顶）并高亮，不用猜现在是哪一档；「设置」是贴在按钮下方的弹出面板（点面板外面、按 Esc、或再点一次「设置」都会收起），可改数据库/日志路径、账号目录、心跳、重连间隔、日志级别、弹幕保留行数、主题（暗色 / 浅色 / 跟随系统，默认暗色）、窗口不透明度
- 导出走命令行（`python -m collector export ...`，见下文），界面上不再放按钮
- 界面分三段：顶部「房间号 + 连接」、「账号（昵称 + 头像）+ 粉丝牌」，中间三栏内容，底部发送区分两行——第一行「表情 · 颜色/位置设置（图标就是当前颜色）· 点赞」，第二行「输入框 + 发送」；Enter 或点「发送」发出（见下节）
- **点赞**：点「点赞」给当前房间 +1（走 `likeReportV3`，参数带 wbi 签名），成功按钮短暂变成「已赞」，tooltip 里记着这次连上后点了多少次；需要登录账号，B 站对该接口有每日上限，超限会回错误原样显示
- 应用图标在 `assets/`（`icon.ico` 带 16–256 六个尺寸，`icon.png` 是预览），由 `tools/make_icon.py` 画出来，想换图案改那个脚本重跑即可；启动时会设成进程图标，任务栏和 Alt-Tab 用的就是它

性能设计：采集在独立线程，界面每 30ms 批量取一次事件，单帧最多渲染 150 条弹幕，超出部分丢弃并计数；弹幕文档限制 600 行自动截断。高密度房间下界面不会积压卡死。

GUI 与命令行共用同一份 `config.json` 和同一个 SQLite 库，可以随时切换。

### 在弹幕机上直接发弹幕

底部输入框发出去的就是正常弹幕，不用再开直播间网页。采集和发送都用账号目录里选中的那个账号。

**账号怎么来**：在 `accounts/`（或设置里指定的目录）放浏览器导出的 cookie 文件，一个账号一个 `.csv`。启动时自动扫描，**合法与否只看有没有 `SESSDATA`**；界面上方（房间号下面）的账号下拉会列出所有能用的账号，显示 B 站昵称和头像（昵称/头像缓存在 `cache/accounts.json`，键是 SESSDATA 摘要，不存明文）。

放在目录里的文件不需要改配置、不用重启：改完目录点「设置 → 保存」就会重扫一遍，弹幕流里会提示加载了几个账号、哪些文件没被当成账号及原因。

**需要什么**：`SESSDATA` 是身份，`bili_jct` 是 CSRF token。两个都在导出的 cookie 文件里。

如果导出的 cookie 里**没有 `bili_jct`**（很常见，它不太显眼），程序会拿 `SESSDATA` 找 `passport.bilibili.com` 换一个，实测能拿到。所以只导 SESSDATA 也能发。

**限制**（B 站服务端的，客户端拦不住的会以错误提示回显）：

| 项 | 值 | 说明 |
|---|---|---|
| 长度 | 80 字符 | 输入框硬限制，粘贴超长会被截到 80；中文也按「个」算，不是字节 |
| 间隔 | 约 1 秒 | 本地先挡一层，提示「发太快了，N 秒后再发」 |
| 权限 | 看账号 | 被禁言、等级不够、需要粉丝牌时会返回 `-403` |
| 颜色/位置 | 看房间 | 见下，房间可以对这两项设限 |

> 长度和间隔都是实测的：80 个字符（中英文混排同理）能发，81 个回 `1003212 超出限制长度`；间隔 1.0 秒连发 4 条全部 `code=0`，压到 0.5 秒才回 `10030 您发送弹幕的频率过快`。所以本地冷却定在 1 秒，不是凭空设的 5 秒。

**颜色和位置**：都在发送按钮右侧的「▾」下拉里（面板上色块网格选颜色、三个按钮选位置，当前值在按钮的悬停提示里也能看到）。**这两个选项不是想选就能生效的**——B 站允许主播对直播间设限（比如只开放白色、只允许滚动，彩色弹幕要粉丝牌或活动期间才开）。所以程序会先问
`GetDMConfigByGroup` 拿到「当前账号 + 当前房间」真正可用的项，只把这些列出来：位置只开放一种时三个按钮全部禁用，色板里只出现能用的颜色。

> 踩过的坑：直接给 `/msg/send` 传 `color`/`mode` 不会报错，`code` 还是 0，但服务端会**静默**把颜色改回白色、位置改回滚动。所以别用「发送成功」判断生效，必须看回显里真实的 `color`/`mode`。

**表情**：点「表情」弹出面板，按表情包分组（房间专属 → 通用 → 装扮 → emoji），图片走后台下载 + 磁盘缓存，点一下就发。分组条一行放不下时可以横向滚（滚轮在条上也能滚）。发送方式分两种，别混：

| 表情包 | 发法 |
|---|---|
| 房间专属、UP主、通用、装扮表情（图片表情） | `dm_type=1`，`msg` 填表情唯一 ID（如 `room_42062_121079`、`upower_[艾尔莎只想宅在家_你先别急]`） |
| emoji（`[dog]` 这类） | 普通文本，`msg` 就是 `[dog]`，前端自己渲染成图 |

> 踩过的坑：图片表情**不能**用名字发（`msg=敢耍俺` 或 `msg=[dog]`），服务端不会报错但只当普通文字；反过来把 unique 当普通文本发也不认。发错通道时图片表情回 `10203 表情发送失败~`。

> **没拉全就是缺 `buvid3`**：同一个账号，cookie 里没有 `buvid3` 时 `GetEmoticons` 只回「通用表情 + 房间专属」两组，把 buvid 补上之后立刻多出 emoji 包（`pkg_type=3`，82 个）和账号自己的**装扮表情**（`pkg_type=5`，几套加起来几百个）。浏览器导出的 cookie 常常漏掉 HttpOnly 的 buvid，所以 `DanmakuSender` 在第一次请求前会用 `x/frontend/finger/spi` 匿名领一对补进去（失败也不影响收发）。表情包缓存按「房间 + 账号 SESSDATA 摘要」分文件，大小号的列表不会互相顶掉。

**粉丝牌**：发送行左边第二个下拉，列出当前账号的全部粉丝牌（`GetMyMedals` 翻页拿全，按等级降序），带「（本房间）」标注的是你在这个主播的牌子。**默认就停在你当前戴着的那枚**（接口里 `status=1` 的那条），不选就不会动你的牌子；**手动换一个会立刻调 `fansMedal/wear` 把账号上的佩戴改成它**（后台线程，失败会在弹幕流里报一句，发送时再试一次），不是等你发下一条才生效。

> **这里有个 B 站服务端的硬限制，实测出来的**：**在某个直播间发弹幕，弹幕上显示的始终是「你在该主播的牌子」**，跟你全局佩戴哪一枚无关。
>
> 证据：账号 コーヒーパワー 有 11 枚牌子，在 42062（主播「瓶子君152」，有 `燃烧瓶 Lv21`）测试——
> - 佩戴 `参拾弐`（房间 22748536）→ 发弹幕，回显仍是 `燃烧瓶 Lv21`
> - 佩戴 `恰个V`（房间 708397）→ 仍带 `燃烧瓶 Lv21`
> - 给 `/msg/send` 加 `medal_id` / `fans_medal_id` 参数 → `code=0` 但同样被忽略
> - `wear` 传 `medal_id=0` 或 `-1` 想摘掉牌子 → `-400 请求错误` / `1500004 主播未开通勋章`
>
> 所以这个下拉的真实作用是「切换全局佩戴」——**选了就真的换，刷新个人空间、别人看你主页都会变**，影响的是个人空间、其他场景，以及**你没有该主播牌子的房间**；它改不了本房间弹幕上那枚。想要的是「这条弹幕换一枚牌子发」的话，B 站没给这个口子（试过“发送前戴、发完换回”，但这等于每条弹幕都在改账号状态，还不如一次换到位）。

**必须先连上房间才能发**：发送行在未连接时是禁用的（输入框、表情、颜色、位置、发送全灰），只有真正连进某个房间、收到「已进入 XXX」之后才会解锁。这么设计不是为了麻烦，是因为早先版本允许拿输入框里的房间号直接发——少按一位就可能发进别人的房间，账号在陌生房间说话还容易触发风控。断开连接的瞬间会立刻锁回去，不发到上一个房间。

**发完看得到吗**：连着房间时，服务端会在不到一秒内把你自己那条弹幕推回来，正常显示在弹幕流里，并且能看到真实的颜色、位置和粉丝牌（这也是验证房间里那些选项有没有生效的唯一办法）。

**换了浏览器要不要重启**：不用。设置里改账号目录、或往目录里加减 csv，保存后立刻重扫并重建发送器，下一次发送就用新账号。切账号（下拉）会顺带清掉表情包、可用颜色和粉丝牌缓存，按新账号重拉。**采集用的身份是连接时定下的**：正在收弹幕时换账号，要点一次「断开」再「连接」，否则这条连接还是旧账号（事件栏里会提示）。

**常见错误**：

- `登录已失效，请重新导出 cookie`（`-101`）：SESSDATA 过期了
- `CSRF 校验失败`（`-111`）：cookie 不完整
- `没有发言权限`（`-403`）：账号在该房间发不了
- `表情发送失败`（`10203`）：这个表情用了错误的发送通道


### 0 号直播间（回放 + 测试发送）

房间号输入 `0` 就是离线回放：不联网、不写库，素材直接取自 `config.json` 里 `database` 指向的采集库。

- **SC 与礼物用原始 payload 回放**：从 `sc_message.raw_json` / `room_event.raw_json` 读出真实记录，再交给生产同一条 `extract_sc()` 解析，等于把「原始 JSON → 字段 → 界面」整条链路跑一遍，改了解析或渲染随时能复现。
- **译文三种到达方式各跑一遍**：本体自带 `message_trans`、`_JPN` 后到、`_JPN` 先到（缓冲合并）。带译文和不带译文各占一半，方便对照界面上「译：」这一行到底出没出。
- **弹幕是最近一场的连续片段**：按 30 分钟空档切场，跳过末尾那种几十秒的零星短场，所以时间戳单调递增，不会突然跳几个小时。
- 回放节奏压慢了（弹幕约 33 条/秒、SC 约 1.5 秒一条），方便肉眼核对每条排版；列表循环播放，每条 SC 的 `sc_id` 加 `-rN` 后缀区分轮次。
- 库里没有可用数据（路径为空、文件不存在、不是本项目的库）时，自动退回原来的合成数据流。
- **可以在这里调试发送**：发送行不会锁死，但发出去的弹幕只在本机回显（右侧带 `[测试 #颜色 · 位置]`），一条都不会出网。没有 cookie 也能点，用来核对颜色、位置、表情和牌子的排版。

只用来看渲染和文案，不需要登录，也不会污染采集库。

```powershell
& ".\.venv\Scripts\python.exe" -m collector run -c config.json --room 6 --room 21452505
```

## 命令

| 命令 | 说明 |
|---|---|
| `run` | 启动采集（常驻） |
| `resolve --room 6` | 解析房间号、验证 token 与节点可用性 |
| `export --format ndjson --out exports/sc.ndjson` | 导出 NDJSON |
| `export --format csv --out exports/sc.csv` | 导出 CSV（UTF-8 BOM，Excel 可直接打开） |
| `stats` | 查看各房间条数与时间范围 |
| `selftest` | 离线自检：三种解包、去重、导出 |

导出支持过滤：`--room 545068`、`--since <unix秒>`、`--until <unix秒>`、`--with-raw`（仅 NDJSON）。

## 表结构

`sc_message`（SC 主表）：

| 字段 | 说明 |
|---|---|
| `sc_id` | B 站 SC id，**主键**，冲突即忽略（去重） |
| `room_id` | 真实房间号 |
| `uid` / `uname` | 发送者 |
| `price` | 价格（元） |
| `message` | 留言原文 |
| `message_trans` | SC 翻译（来自 `SUPER_CHAT_MESSAGE_JPN`，无翻译时为 NULL） |
| `start_time` | B 站 Unix 秒（权威时间） |
| `end_time` | B 站 Unix 秒，SC 停留结束时间 |
| `received_at` | 本地收到时刻，Unix 毫秒 |
| `guard_level` | 舰队等级（0 普通 / 1 总督 / 2 提督 / 3 舰长） |
| `medal_name` / `medal_level` / `medal_anchor_roomid` / `medal_color` | 粉丝勋章 |
| `raw_json` | 整条原始 payload |

`sc_deletion`：SC 删除事件，一条记录对应一个被删 `sc_id`，原始 JSON 同样保留。
`collect_room`：采集过的房间信息（标题、主播名）。

`room_event`（进场 / 礼物 / 上舰 / SC 删除，**所见即所得**：事件栏里勾选该类型且事件栏可见时才写入，取消勾选或隐藏事件栏则既不显示也不落库；弹幕与 SC 不受影响，始终入库）：

| 字段 | 说明 |
|---|---|
| `seq` | 自增主键 |
| `room_id` | 真实房间号 |
| `event_type` | `enter` 进入直播间 / `gift` 礼物 / `guard` 上舰 / `delete` SC 删除 |
| `event_key` | 去重键：礼物用 `tid`，进场用 `uid:时间:msg_type` |
| `uid` / `uname` | 用户 |
| `gift_name` / `gift_num` / `price` / `coin_type` | 礼物信息（仅 `gift`） |
| `event_time` | B 站 Unix 秒 |
| `received_at` | 本地收到时刻，Unix 毫秒 |
| `raw_json` | 整条原始 payload |

唯一索引 `(room_id, event_type, event_key)`，重复事件自动忽略。

> 进场事件实际走 `INTERACT_WORD_V2`，用户信息在 `data.pb` 的 protobuf 里（字段 1=uid、2=uname、5=msg_type、6=room_id、7=时间戳），由 `protocol.parse_interact_word_v2` 解析。

索引：`(room_id, start_time)`、`start_time`、`received_at`。

## 时间对齐录播

- 以 `start_time`（B 站 Unix 秒）为准，与录播时间轴一致；
- `received_at` 是本地墙钟毫秒，实测与 `start_time` 相差约 0.7 秒（网络 + 服务端推送延迟）；
- 导出里的 `start_offset_seconds = received_at/1000 - start_time`，可用于估算链路延迟；
- 同秒多条 SC 时，`start_time` 无法区分顺序，需要时用 `received_at` 或 `sc_id` 兜底排序。

## 注意事项

- **SC 是低频事件**。热门房间也可能几分钟才一条，日志里 `sc=0` 属正常。
- **匿名连接的普通弹幕昵称会被 B 站打码**（如 `青***`），这是服务端行为，不是本地截断。界面里选了账号再连就是登录态，昵称完整、也带粉丝牌/舰长信息；命令行默认匿名，不选账号的纯匿名采集就会看到打码。
- **表情图来自 `i0/i1.hdslb.com`**，断网时只影响这一张小图，文字照常显示。`room=0` 回放的历史弹幕没有表情图——库里从来没存这一列，只有新采集的才带。
- SC 翻译来自紧随其后的 `SUPER_CHAT_MESSAGE_JPN`，按 `id` 回填到 `message_trans`；没有翻译的 SC 该字段为空。
- 进场事件在热门房间量很大（30 秒 60 条量级），不需要时取消事件栏的「进场」勾选即可，显示与入库会同时关闭。
- 协议上无法只订阅 SC，必须收全量弹幕再本地过滤；房间越热，带宽和解析开销越大。
- 断线期间 B 站不补发 SC，重连后无法自动补齐历史；需要精确补录时用 `getInfoByRoom` 对账（匿名可见性有限）。
- 匿名连接受风控约束：同 IP 挂过多房间或高频重连可能被临时拒绝，表现为鉴权失败并触发退避重连。
- token 与 `roomid` 强绑定：必须用同一房间号取 token 并鉴权，否则服务端会直接断开连接。
